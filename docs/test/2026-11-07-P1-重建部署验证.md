## 三、这次踩到的新坑（写下来别再踩）

1. **1Panel 文件 API 看不见 `/opt/1panel/apps` 与 `/opt/1panel/docker/compose`**
   宿主上这两个目录根本不存在（`ls` 报 No such file），但 docker 容器 label 里写着 `com.docker.compose.project.working_dir=/opt/1panel/docker/compose/csx-standalone`。
   所以：**别信 compose 记录里的路径**，用一次性容器挂 `/:/host` 亲自 `ls` 一遍再决定往哪写。真实可写目录是 `/opt/csx-standalone`。
2. **`/tmp` 是面板与宿主共享的**（实测：文件 API 上传到 `/tmp` 的文件，宿主 `/host/tmp` 里能看到）
   → 上传 tar 到 `/tmp` 再用一次性容器 `tar xzf /host/tmp/xxx.tar.gz -C /host/opt/...` 是最省事的发布通道。
3. **1Panel 这个版本没有容器日志接口**：`/api/v2/containers/logs`、`/logs/{id}`、`/log` 全 404
   → 一次性容器的输出别指望看日志，让它把结果写进 `/host/tmp/xxx.txt`，再用 `files/content` 读回。
4. **删除文件的接口是 `POST /api/v2/files/del`**，不是 `files/delete` / `files/remove`（后两个 404）。
5. `compose/operate` 的 `operation:"delete"` 只删面板记录，不删数据卷；配合 `containers/operate {"operation":"stop","names":[...]}` 才能安全换实现。
6. `files/search` 对不存在的目录返回**空结构而不是报错**（`items:null`），容易误判成「目录为空」。

## 四、发布 SOP（下次照这个做）

```
1. 本地 tar czf /tmp/csx.tar.gz --exclude={.git,node_modules,__pycache__,data,dist,*.db,.venv} csx-standalone
2. curl -F path=/tmp -F file=@/tmp/csx.tar.gz  POST /api/v2/files/upload
3. 建临时 compose（alpine + /:/host）→ 备份数据卷 → rm -rf /host/opt/csx-standalone → tar xzf → 结果写 /host/tmp/step.txt
4. files/content 读 /tmp/step.txt 确认
5. containers/operate stop 旧容器
6. compose/operate delete 旧记录 → compose（from:edit）新建同名记录 → operate up（镜像 tag 必须变）
7. inspect 看 Image/Health；curl 公网 /health /login /api/v1/meta 401 / 登录 200
8. 一次性容器 sqlite3 验 alembic_version 与 admin_user 仍在
9. 删临时容器、临时 compose 记录、/tmp 临时文件
```
