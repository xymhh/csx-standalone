# TG 频道监控客户端 · 调研

> 状态：已完成，结论=移植插件实现到 CSX 独立模块 → 见 `2026-11-09-TG客户端-架构.md`

## 1. 需求

CSX 已有 `POST /api/v1/tg/ingest`（外部推送文本 → 解析 → 匹配订阅 → 建候选/任务），
但频道消息靠外部系统推入。目标：CSX 自己用用户账号（api_id / api_hash / StringSession）
定时拉取频道新消息，直接走 ingest 逻辑，不依赖 MoviePilot。

## 2. 现成方案对比

| # | 方案 | star / 活跃度 | 许可 | 覆盖能力 | 差距 |
|---|---|---|---|---|---|
| 1 | **Telethon** | ~10.6k / 2025 活跃 | MIT | 用户账号登录、`iter_messages`、StringSession、FloodWait 异常、async | 需要自己写调度与游标（约 300 行） |
| 2 | Pyrogram | ~11.3k / 2024 后维护放缓 | LGPL-3.0 | 同上，API 更简洁 | session 格式与插件不兼容（用户已从插件迁出 StringSession）；LGPL 传染性需评估 |
| 3 | aiogram | ~5.2k / 活跃 | MIT | Bot API 封装 | **不能用用户账号读私有频道**，只能收 bot 能看到的更新 |
| 4 | telethon + cryptg | — | Apache-2.0 | 为 Telethon 提供 C 加速 | 仅性能，不解决能力；镜像体积 +几 MB，可选 |
| 5 | 直接移植插件 `core/tg_monitor.py`（2307 行） | 自有代码 | — | 已跑通：多频道规则、游标、FloodWait、自动转存、验证码登录 | 深度耦合 `PluginBase` / `self._save_config` / MP 的 `transfer` 服务，不能直接搬 |
| 6 | Telegram 归档工具（tg_channel_downloader 等） | 各有千级 | GPL/MIT | 下载频道文件到本地 | 定位是下载媒体，不产出「网盘分享链接 → 订阅匹配」，且不提供库调用 |

本地检索：`csx-standalone` 内无任何 telethon/客户端实现；`moviepilot-plugins-cs/plugins.v2/cloudsubscribex/core/tg_monitor.py` 是唯一可参考实现。

## 3. 结论

**改造（③ 移植）**：以 Telethon 为客户端（与已迁入的 StringSession 完全兼容），
把插件 `tg_monitor` 的**扫描骨架**（游标、FloodWait、频道归一化）抽成 CSX 独立模块，
业务落地直接复用 CSX 现有的 `ingest_telegram_message`，不搬运插件的转存/规则引擎。

不做的事（明确划出范围）：
- 不实现手机号 + 验证码交互登录（用户在插件侧已完成登录并导出了 session；CSX 只接收 session 串）
- 不搬插件的「每频道规则（关键词/白名单/画质偏好）」—— CSX 的订阅匹配已经决定要不要收
- 不实现媒体文件下载
