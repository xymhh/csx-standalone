# P4 任务书：资源式 API + 任务调度器 + SSE 事件流

> 状态：待开工
> 前置：P0 骨架、P0.5 鉴权、P1 领域/持久化、P2 驱动与搜索、P3 转存与整理均已完成（194 测试全绿）
> 预计：7 人日（委派约 3–4 小时机时）

## 0. 本阶段目标（一句话）

把 P1 的数据模型、P2 的驱动/搜索注册表、P3 的转存整理编排，通过一套**统一包络、会话保护的 RESTful 资源路由 + 后台任务调度器 + SSE 事件流**暴露出来，收敛旧插件的 95 个杂乱端点，为 P5 前端提供完备的 API。

## 1. 资源路由规范（统一前缀 `/api/v1`，全受 cookie 鉴权保护）

所有响应必须走统一包络：`{"ok": bool, "data": ..., "error": {"code": str, "message": str, "hint": str | None}}`。

### 1.1 订阅 `/api/v1/subscriptions`
- `GET /subscriptions`：列表（支持按 `state=active|paused`、`keyword` 过滤，分页 `page, page_size`）
- `POST /subscriptions`：新建订阅（输入：`media_id/tmdb_id, scope, quality_pref, source`）
- `GET /subscriptions/{id}`：详情（含媒体信息、季集范围、命中规则）
- `PATCH /subscriptions/{id}`：更新（改 `state` 暂停/恢复、改范围、改画质偏好）
- `DELETE /subscriptions/{id}`：删除（软删改 state=deleted 或真删）
- `POST /subscriptions/{id}/sync`：立即触发该订阅的搜索与发现（产生候选资源）

### 1.2 进度表 `/api/v1/progress`
- `GET /progress`：全量追更进度概览（基于 `media_item + season + episode + library_file` 聚合：已播数、已入库数、缺失集清单）
- `GET /progress/{media_id}`：单剧完整追更矩阵（季/集/播出日期/入库状态/对应文件画质）

### 1.3 候选池 `/api/v1/candidates`
- `GET /candidates`：候选资源列表（按 `subscription_id`、`state=discovered|accepted|ignored` 过滤）
- `POST /candidates/{id}/accept`：手动采纳候选 → 按 `idempotency_key` 创建 `transfer_task` 并进入 `queued`
- `POST /candidates/{id}/ignore`：忽略候选

### 1.4 任务队列与控制 `/api/v1/tasks`
- `GET /tasks`：任务列表（按 `state=queued|running|retry_wait|dead_letter` 过滤）
- `POST /tasks/{id}/retry`：手动重试（将 `retry_wait` 或 `dead_letter` 的任务重置为 `queued`，attempt 归零）
- `POST /tasks/{id}/cancel`：取消排队中的任务

### 1.5 历史记录 `/api/v1/history`
- `GET /history`：已终态任务列表（`state in (succeeded, dead_letter)`），支持按时间范围、provider 过滤与分页
- `POST /history/retry_batch`：批量重试指定死信任务

### 1.6 媒体库与文件 `/api/v1/library`
- `GET /library/files`：入库文件列表（按 media_id、分页）
- `GET /library/servers`：媒体服务器状态（Emby/Jellyfin 连通性，当前桩实现即可，P6 补齐）

### 1.7 设置 `/api/v1/settings`（必须分 6 组，严禁平铺 226 个散键）
- `GET /settings`：获取全部分组配置
- `GET /settings/{section}`：获取指定分组配置
- `PUT /settings/{section}`：全量/增量更新指定分组配置（JSON 验证）
- `POST /settings/test/{provider}`：测试指定网盘/服务连通性

**6 大分组定义**：
1. `baseline`：基准面配置（最小缺集窗口、默认语言、时区）
2. `sources`：双源与搜索源配置（启用的搜索源、搜索超时、并发限制）
3. `transfer`：转存与洗版配置（默认网盘、转存临时目录、洗版策略、画质偏好顺序）
4. `strm`：STRM 生成配置（根目录、URL 模式、内网外网地址映射）
5. `notify`：通知渠道（Webhook 地址、通知事件开关）
6. `advanced`：高级与诊断（日志级别、调度周期、令牌桶速率）

### 1.8 网盘账号 `/api/v1/accounts`
- `GET /accounts`：已配网盘账号列表（屏蔽敏感 cookie/token，只回显脱敏值或状态）
- `POST /accounts`：添加账号（provider, credential, name）
- `PATCH /accounts/{id}`：更新账号（改名称、更新凭据）
- `DELETE /accounts/{id}`：删除账号
- `POST /accounts/{id}/test`：测试账号有效性（调对应驱动获取用户信息或根目录）

### 1.9 诊断 `/api/v1/doctor`
- `GET /doctor`：系统自检诊断
  - 数据库连通与大小
  - 各已配网盘连通性与配额
  - 调度器运行状态（当前活跃 worker 数、等待队列深度）
  - 磁盘空间与数据目录读写权限

### 1.10 实时事件 `/api/v1/events`（SSE 流）
- `GET /events`：Server-Sent Events 端点
  - 事件类型：
    - `task_status`：任务状态变更（task_id, old_state, new_state, error）
    - `candidate_found`：新候选发现
    - `progress_update`：追更进度刷新
    - `heartbeat`：每 15 秒心跳保活
  - 支持多客户端同时订阅，断开自动清理监听器

## 2. 后台任务调度器 `csx/infra/scheduler.py`

基于 `APScheduler`（已有依赖）或轻量 `asyncio.Task` 循环构建后台调度器：

1. **周期巡检**（默认每 30 秒）：
   - 调用 P1 `TaskRepository.due(now)` 捞取到期的待执行任务（queued 或 retry 到期）
   - 将捞到的任务派发给 worker 执行
2. **并发控制与令牌桶**（严格照架构冻结参数）：
   - 全局最大并发：`8`
   - 同一 `idempotency_key` 串行执行
   - 账号级令牌桶：
     - `115`：4 次/分钟
     - `quark`：8 次/分钟
     - 其他网盘：默认 4 次/分钟
   - 任务超出并发限制时留在队列中排队，不丢弃
3. **执行与重试**：
   - 驱动调用必须包在 `run_in_threadpool` 里，绝不能卡主事件循环
   - 调 P3 `execute_transfer` 执行
   - 状态迁移完成后广播 SSE 事件
4. **生命周期集成**：
   - 在 `csx/api/main.py` 的 `lifespan` 中随应用启动和停止

## 3. 依赖方向与边界铁律

1. `api/routes/*` 只能依赖 `application/*`、`domain/*`、`ports/*`、`infra/*`（db/settings/logging/envelope）
2. **`api/` 和 `application/` 严禁直接 import `csx.vendor`**（只有 `adapters/drive/*` 允许）
3. 所有 `/api/v1/*` 端点（除 health 和 `/api/v1/auth/login`）自动被现有 `auth_guard` 拦截，需登录态
4. 现有 194 个测试一行不许改，全部保持绿灯
