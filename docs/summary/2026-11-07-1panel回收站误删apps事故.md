# 1Panel 回收站与 `/opt/1panel/apps` 误删事故（2026-11-07）

> 状态：已恢复，生产验证通过。事故责任人：我（agent 专用 API Key）。

## 1. 一句话

`/.1panel_clash` 是 1Panel 的**回收站**，不是文件服务存储根。我在 2026-11-07 05:18:20 用 `files/del` 把 `/opt/1panel/apps`（19.86 GB / 31 个应用）和 `/opt/1panel/docker/compose` 整体删了进去；因 `files/del` 实为 `rename`，19 个容器仍在运行，但**任何容器重启都会挂到空目录**。当日已完整还原并验证。

## 2. `/.1panel_clash` 到底是什么

| 证据 | 内容 |
| --- | --- |
| 源码 | `agent/init/dir/dir.go:33` `global.Dir.RecycleBinDir = "/.1panel_clash"` |
| 保护逻辑 | `agent/app/service/file.go:292` 禁止删除该目录本身（`ErrPathNotDelete`） |
| 目录结构 | `files/<hash>`（内容）+ `info/<hash>.trashinfo`（freedesktop 标准元数据） |
| 元数据样例 | `Path = %2Fopt%2F1panel%2Fapps`、`DeletionDate = 2026-11-07T05:18:13`、`Size = 19864530944` |
| 行为 | 面板删除文件 = `rename()` 进回收站；`FileRecycleBin` 设为 Disable 才真删 |

**为什么"以前没这目录"**：名字以 `.` 开头（`ls /` 看不见）；只有删过东西才会产生内容；本机 2026-10-04 装面板，第一次产生内容是 11-03 17:51（删 `apps/_mig`）。

## 4. 影响

- `files/del` 是 `rename`，**inode 未变** → MP / Gopeed / Emby / OpenList 等 19 个容器仍在正常读写
- `/opt/1panel/apps` 路径消失 → 任何容器**重启即挂空目录**；`build.context` 指向该路径必然失败（退化成 pull）
- 此前判断的「MP bind 源在守护进程解析不到」根因即此
- 期间把 `csx-standalone` "迁到 MP 同级"实际是放进了回收站里的 apps 副本

## 5. 恢复步骤（已执行）

1. `mv /.1panel_clash/files/b249cde2… /opt/1panel/apps`（同文件系统 rename，秒级，inode 不变）
2. `docker/compose` 目录按「目标已存在则合并补缺文件、缺失则整目录搬回」处理；`csx-standalone` 保留事故后重建的新版，不覆盖
3. 删除两份 `.trashinfo`
4. 补建缺失的 bind 源 `/opt/1panel/apps/openlist/data/temp/aria2`
5. 清理本次排查建的一次性容器与 compose 记录（`csx-q4…q10`、`q4…q10`、`csx-q/csx-q2/csx-q3`）

## 7. 教训（写成硬约束）

1. 禁止对 `/opt/1panel/apps`、`/opt/1panel/docker/compose`、`/opt/1panel/db` 这类**父目录**执行 `files/del`
2. 删任何路径前先 `files/search` 确认 path 是目标叶子目录
3. 出现 `files/del [path]` 这类"参数没展开"的失败，**先停下查变量**，不许改路径硬重试
4. 1Panel 的"删除"是进回收站，不是销毁 —— 出事第一反应去 `/.1panel_clash/info/*.trashinfo` 查原路径与删除时间，而不是找备份
